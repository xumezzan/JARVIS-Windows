# Переустановка актуальной версии одним запросом в Codex

На уже установленном Windows-ноутбуке достаточно попросить:

> Установи заново последнюю версию Jarvis из GitHub, сохрани мои настройки и проверь результат.

После получения этой версии репозитория `AGENTS.md` также связывает короткое «установи
заново» с обновлением из опубликованного `main`. Codex закрывает только наблюдённые окна
Jarvis после завершения/отмены его задачи, запускает обновление, читает отчёты и проверяет
настоящие окно и ярлык. Python/pip вручную не готовятся. OAuth, секреты и OS consent
по-прежнему принадлежат пользователю.

```powershell
& '.\scripts\windows\Update-Jarvis.cmd'
if ($LASTEXITCODE -ne 0) { throw 'Update did not pass; inspect the report path printed above' }
Get-Content -Encoding UTF8 -LiteralPath "$env:LOCALAPPDATA\JarvisInstall\installation-report.md"
Get-Content -Encoding UTF8 -LiteralPath "$env:LOCALAPPDATA\JarvisInstall\installation-bootstrap.md"
```

## Что делает сценарий

1. Проверяет Git и ожидаемый `origin` проекта. Не меняет remote, не запрашивает и
   не сохраняет credentials. Для загрузки используется публичный HTTPS репозиторий
   `xumezzan/JARVIS-Windows`; URL rewrites требуют отдельного рассмотрения.
2. Получает точный коммит опубликованного `main`; ветка разработки и неподготовленные
   изменения на Mac не являются каналом обновлений.
3. Чистый `main`, который можно fast-forward, обновляет без переписывания истории.
   При изменениях, другой ветке, detached HEAD или расхождении истории готовит отдельный
   detached Git worktree. Исходная ветка и пользовательские файлы остаются на месте.
4. Запускает `Install-Jarvis.cmd` из выбранного источника с точным source commit.
   Существующий установщик готовит и проверяет неактивный слот перед активацией.
   Память, настройки и OS credentials находятся отдельно от слотов.
5. Сверяет коммит и чистоту источника, результаты установки, bootstrap и их `run_id`.
   Успех только загрузки не выдаётся за установленное обновление.

Каждая команда Git ограничена 180 секундами; помощник завершается при timeout.
Raw Git stdout/stderr и содержимое пользовательских файлов в отчёт не сохраняются.
Hooks и fsmonitor не вызываются. Нет reset, clean, stash, rebase или скрытого удаления.
Изолированный worktree сохраняется для проверки вместе с его отчётом: не удаляйте его
или исходный репозиторий во время установки. Автоматической очистки таких копий нет.

## Отчёты и повтор

Путь к `%TEMP%\JarvisUpdate-<ID>\update-report.md` выводится в начале. Рядом лежит JSON:
предыдущий коммит исходников, полученный коммит, способ обновления, каталог источника,
этап, время и идентификатор установки. `source_ready` означает только подготовку исходников
с `-SkipInstall`; `updated` — проверенную установку указанного источника. `failed` и
незавершённый `running` не являются обновлением.

`installation-report.json` schema 2 и его Markdown, а также bootstrap содержат
`source_commit`. Совпадение commit/run_id и успешные автоматические проверки необходимы
для результата обновления. Полная native-приёмка, реальные аккаунты и оборудование
остаются отдельными воротами: [WINDOWS_ACCEPTANCE.md](WINDOWS_ACCEPTANCE.md).

Если сеть недоступна, обновление останавливается и не объявляет старую версию новой.
Для явно запрошенного локального ремонта или проверки повторной установки без сети:

```powershell
& '.\scripts\windows\Install-Jarvis.cmd'
```

Ошибка установки не доказывает автоматического отката: сбой ярлыка или отчёта возможен
после активации. Проверить actual `active.json`, отчёты и окно. Никогда не удалять
пользовательские данные, credentials или рабочий слот ради обновления.

## Если на старом ноутбуке ещё нет Update-Jarvis.cmd

Первый приведённый запрос явно требует последнюю версию из GitHub. Codex должен получить
её перед установкой, даже если старый `AGENTS.md` описывал только локальный Install:
inspect status/origin → fetch main → определить SHA → fast-forward чистого main либо
создать отдельный checkout → читать новые инструкции → запускать installer этого checkout.
При отсутствии Git использовать доступный Codex Git workflow или подготовить официальный
Git с обычными OS согласиями; Python вручную не нужен. Не запускать старый installer
и не считать это загрузкой последней версии.

Обновления доступны другому компьютеру только после публикации и слияния в `main`.
Эта инструкция не означает, что данный прогон уже выполнен на целевом Windows-ноутбуке.
