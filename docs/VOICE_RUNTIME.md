# Голосовой runtime и headless Electron

Изменение по запросу пользователя от 24 октября 2026. Исходный отчёт этапа 6 сохранён
в [MILESTONE_6.md](MILESTONE_6.md). Это не завершение Windows acceptance или следующих milestones.

## Постоянный AudioHost

Обновление 2026-10-25: [wake word, адаптивный RMS и HUD](WAKE_WORD_HUD.md).
По умолчанию сохраняется push-to-talk. Только явный startup opt-in
JARVIS_VOICE_WAKE_WORD=1 разрешает Electron локально ждать «Джарвис» с видимым
индикатором микрофона; команда записывается через EnergyEndpoint. Qt остаётся
в режиме ручной записи. Wake не выдаёт approvals/cloud consent и не включает autostart.

`voice/host.py` владеет отдельным asyncio-loop в служебном потоке и долгоживущим
`jarvis.platforms.audio --recognition-host`. При запуске голосовой панели/сервиса с настроенным
`JARVIS_VOSK_MODEL` он заранее загружает **локальный** `vosk.Model` один раз. Для каждого
PCM создаётся новый KaldiRecognizer: модель переиспользуется, состояние отдельных фраз — нет.
Хост работает между короткими Qt VoiceWorker loops и в Electron. Смена модели закрывает
старый хост; завершение приложения останавливает процесс и поток.

По умолчанию микрофон и системный TTS остаются отдельными ограниченными killable
helpers. Опциональный VAD использует record-операцию того же AudioHost с уже загруженной
моделью, только после существующего UI-жеста; TTS в этом процессе нет.
Аудио передаётся ограниченными JSONL-пакетами через pipe,
не записывается в файлы, не передаётся через argv и не отправляется в облако. Повреждение
pipe, превышение лимита, отмена и timeout завершают и reap-ят процесс; уже выданная фраза
не повторяется. Следующая новая пользовательская запись может создать новый хост.

Устранена повторная загрузка модели на каждую фразу. **Задержка 50–100 мс не измерена и
не гарантируется:** она зависит от модели, длительности записи и целевого устройства.
Обычный старт не скачивает модель и не включает микрофон.

## Опциональное завершение фразы по тишине (2026-10-25)

Startup-параметр `JARVIS_VOICE_AUTO_STOP_ON_SILENCE=1` включает режим в Qt и Electron.
Default `0` сохраняет ручной release. Для прямой композиции адаптеров:
`LocalRecorder(host=recognizer.host, auto_stop_on_silence=True)`.

Каждый блок — 1600 PCM16 samples / 100 мс. Чистый `EnergyEndpoint` считает RMS;
три последовательных блока с RMS >=500 отмечают начало фразы, после которого
12 последовательных тихих блоков (1.2 секунды) завершают запись. Начальная тишина
не завершает фразу, возобновление речи сбрасывает счётчик тишины.
По умолчанию порог 500. JARVIS_VOICE_RMS_THRESHOLD задаёт конечное число 1..32768;
опциональный JARVIS_VOICE_RMS_CALIBRATE=1 использует первые два тихих кадра и
порог 3×средний RMS шума (не ниже 50). Калибровка заканчивается до начала речи;
без начальной тишины сохраняется заданный порог. Подбор под реальное устройство
не подтверждён fixtures.

Для streaming `KaldiRecognizer.AcceptWaveform()` используется ограниченная очередь
из восьми блоков, обработка вне native audio callback; overflow прерывает запись.
AudioHost загружает модель один раз, на capture и transcribe создаются отдельные
декодеры. Native record исполняется в одном потоке, а управляющий цикл принимает
только stop с точным capture_id; старая остановка не затрагивает следующую запись.
Ручной release, focus loss, Stop/Escape, timeout и kill/reap продолжают действовать.
Автоостановка не запускает микрофон, не подтверждает действия и не даёт cloud consent.
PCM/расшифровка не сохраняются. Проверки записаны в [SOM_VAD_FIXES.md](SOM_VAD_FIXES.md).

## Автозапуск и естественный отчёт

«Голосовой автозапуск» выключен по умолчанию и действует в текущем сеансе. При включении
и `confidence >= 0.75` распознанный текст запускает прежний Runner; параллельно системный
голос отвечает «Принял, выполняю». При меньшей уверенности текст остаётся для проверки.
Голосовые «стоп»/«отмена» отменяют задачу. Речь не выдаёт разрешения на действия.

Автозапуск не даёт согласия на OpenAI и не снимает CONFIRM. Для облачного запроса в
Electron нужно проверить расшифровку, отметить согласие на одну задачу и запустить её.
Согласие на передачу выбранной памяти остаётся отдельным. Настройка озвучивания итога
независима от автозапуска. Итоговая речь не возобновляется после Stop во время смены озвучки.

`Proposal(kind="finish")` поддерживает `spoken_summary` до 300 символов; для call/clarify
поле должно быть пустым. Строгая Responses API control-schema содержит это поле. Runner
переносит текст в PlanResult. При `finished` он озвучивается вместо стандартного шаблона;
при симуляции, отсутствии действий, ошибке, отмене, timeout или лимите остаются явные
детерминированные сообщения. Старые провайдеры без поля используют прежний fallback.

Отчёт модели — недоверенная формулировка, а не доказательство выполнения. Фактические
статусы, результаты и аудит определяет PermissionEngine. Инструкция модели требует
русский язык, опору на SUCCESS и запрещает выдавать принятый почтовый запрос за доставку.
Точность этой формулировки на живой модели не проверена. Raw results автоматически не
попадают в речь; модель может ошибиться или включить нежелательные сведения.

Системный голос не передаёт текст в сеть. В Electron ElevenLabs требует загрузки
голосов/проверки Free-лимита и одноразового согласия на **уже показанный точный итог**.
После одной озвучки, отмены, новой задачи или изменения настроек это разрешение исчезает.
Сохраняются проверки аккаунта, тарифа Free, overage, квоты и фиксированных endpoint-ов.
Наследуемая Qt-панель сохраняет существующий сценарий согласия на один следующий итог.

## Electron без Qt

`desktop/service.py` создаёт Runner, PermissionEngine, BrowserHost, MailSession и
DesktopVoice напрямую. В этом процессе нет PySide6, QApplication, PlannerWindow,
ApprovalDialog или QThread. Qt-оболочка `python -m jarvis` сохранена отдельно.
Падение или отсутствие Qt platform plugin не участвует в запуске Electron backend.

JSONL-запросы ограничены 128 KiB, ответы — 1 MiB. Больший ответ нужен для полного точного
approval-снимка и ограниченных данных памяти/почты; подтверждаемые данные не обрезаются.
Каждая операция имеет строгую схему. Произвольных инструментов, shell, selectors или
ключей approval в запросах нет. Все реальные инструменты выполняются через PermissionEngine.

В React встроены:

- Диалог точного действия: полный snapshot, режим, цель и таймер. Ответ связан с ID
  ожидающего prompt и signature; Python выдаёт и атомарно потребляет capability после
  durable audit. Истёкший, повторный, изменённый или отменённый ответ не исполняется.
- Уточнения задачи: ответ идёт в Runner как пользовательские данные, без права approval.
- Удержание микрофона мышью/пробелом, release, Stop/Escape, focus loss и close. Только
  `event.isTrusted` в изолированном preload открывает gesture-канал. Обычный `.click()`
  или `dispatchEvent()` не запускает запись и не подтверждает действие. Main проверяет
  sender/frame/URL, видимость, фокус и ожидающий prompt. API `approve`/`voiceStart` не
  экспортируются в renderer. Микрофон браузера по-прежнему запрещён.
- Настройки провайдера/голоса, выбранная память и управление профилем/контекстом сеанса.
- Подключение Outlook с явным согласием, локальные/удалённые черновики, чтение, точная
  отправка и вложения до 32 KiB через системный file picker. Секреты/токены остаются в OS
  credential store. Смена/отключение аккаунта очищает локальные данные. 202 не доказывает доставку.

Микрофон не работает одновременно с озвучиванием. При задаче запись принимает только
отмену. Renderer crash и закрытие приложения отменяют принадлежащие ему операции.

## Воспроизводимая проверка

На macOS использовано отдельное `/tmp/jarvis-voice-venv` с editable-установкой
`.[dev,voice]`; Pillow установлен для существующего unit-теста обработки изображений.
Старый `.venv` в checkout указывает на отсутствующий каталог, он не заменялся.

```sh
python -m pytest
python -m ruff check .
python -m ruff format --check .
python -m mypy --no-incremental
QT_QPA_PLATFORM=offscreen python -m jarvis --smoke-test
python -m build
npm --prefix desktop run build
JARVIS_PYTHON=/tmp/jarvis-voice-venv/bin/python QT_QPA_PLATFORM=invalid-plugin npm --prefix desktop run qa:electron
JARVIS_PYTHON=/tmp/jarvis-voice-venv/bin/python npm --prefix desktop run qa:voice
```

`qa:electron` использует настоящий backend и реальный `system.info` на Mac.
`qa:voice` запускает отдельный test-only composition root `tests/desktop_runtime_fixture.py`:
реальные Electron/JSONL/Runner/PermissionEngine и пользовательские жесты, искусственные
PCM/STT/TTS, без устройств, аккаунтов и сети. Fixture не импортируется production-сервисом.
Проверены мышь/пробел, focus loss, synthetic gestures, автозапуск, точный UI approval.
Python-тесты проверяют переиспользование модели, новые декодеры, разные asyncio loops,
kill/reap при отмене/timeout/ошибке, порог уверенности, отсутствие поздней речи после Stop,
истечение/повтор/подмену prompt, отказ аудита, сохранность памяти/черновиков/вложений и
одноразовое согласие на ElevenLabs. Бэкенд также запускается subprocess-тестом с неверным
Qt platform plugin.

по существующему пользовательскому референсу. Аппаратную и Windows-приёмку это не заменяет.

с проверкой совместимости и Windows-цели; данный отчёт не заявляет production readiness.
