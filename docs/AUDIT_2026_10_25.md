### Проблема исходного окружения

`.venv` — неработающая ссылка на отсутствующий cache-каталог.
В `.venv-reference` editable `.pth` имеет macOS-флаг `hidden` и игнорируется Python.
Первый запуск с PYTHONPATH дал `752 passed, 2 failed in 13.77s`:

- `tests/unit/test_outlook.py::test_attachment_helper_regular_size_and_symlink` — `MailFailure: mail_attachment`.
- `tests/unit/test_voice.py::test_missing_model_fails_without_microphone_or_network` — ожидался `model`, получен `voice_failed`.

Причина: изолированные `python -I -m jarvis...` helpers игнорируют PYTHONPATH
и не находят установленный пакет. После `chflags nohidden` import временно заработал,
но флаг появился снова; повтор в этом окружении дал те же 2 падения, 752 passed за 13.37s.
Причина повторного появления флага не установлена. Финальная верификация проведена
в отдельном исправном venv; существующая `.venv-reference` не объявляется исправленной.

`Registry Risk` — буквальное значение из discover(), а не риск каждого возможного вызова.
PermissionEngine рассчитывает фактический риск по нормализованным аргументам:
Enter/Alt+F4, чувствительные/координатные clicks и overwrite требуют CONFIRM;
Ctrl+A/Ctrl+C/Ctrl+V/Tab и обычные именованные элементы могут быть SAFE.
У Ctrl+V дополнительно требуется точный digest наблюдавшегося clipboard.
Browser click/close также имеют динамический классификатор.
Проверено prepare(): Ctrl+A=SAFE, Enter=CONFIRM, Alt+F4=CONFIRM.

Qt PlannerWindow по умолчанию сохраняет четыре явно учебных `local.*` инструмента.
Они не являются реализациями новых Windows-возможностей. В DesktopService их нет;
вместо них зарегистрирован настоящий `system.info`.

## Проблемы и ограничения

### P2 — screenshot заслоняет UIA-наблюдение для click

`src/jarvis/core/planner/runner.py:337-344` начинает с самого нового Windows-результата
с совпадающим target. Если это active-window screenshot, `elements=[]` и
`window_rectangle=None`. Метод сразу возвращает False и не ищет подходящее
предыдущее UIA-наблюдение. Native capture действительно возвращает target, но не
элементы и не window_rectangle (`src/jarvis/platforms/windows/native.py:531-559`).

Чистое воспроизведение на schema-valid синтетических snapshots с настоящими
Runner, PermissionEngine и реестром (без вызова Windows adapter):

- inspect → click по наблюдавшемуся элементу: `_observed_target(action) is True`.
- inspect → screenshot с тем же target → тот же click: False.

В штатном run() это приводит к `error / unobserved_target` до approval/вызова адаптера.
Текущие unit-тесты проходят, поскольку отдельного regression case с этим чередованием нет.
Исправление требует явного решения о свежести observation: либо связывать screenshot
с актуальным UIA snapshot, либо искать полное подходящее наблюдение при сохранении
native revalidation и правил свежести. В рамках аудита код не изменялся.

### Set-of-Marks отсутствует

Есть UIA-элементы с runtime_id/rectangle и независимый JPEG capture.
Нет нумерованных отметок, их отрисовки на изображении, схемы mark_id,
таблицы соответствия маркер → ElementTarget или передачи размеченного кадра.
В capture нет ImageDraw/нанесения отметок. Связность Set-of-Marks не подтверждается,
поскольку сама возможность не реализована. Это не скрытый pass или fake success.

### AudioHost реализован; отдельного VAD нет

AudioHost действительно владеет постоянным asyncio loop и helper-процессом;
recognition-host загружает vosk.Model один раз, создавая KaldiRecognizer на высказывание.
Запись использует sounddevice.RawInputStream, ограничение PCM и остановку по UI/таймеру.
`len(pcm) < 3200`, пустой transcript и Vosk endpoint segmentation не являются
отдельным VAD для обнаружения/автоостановки записи. VAD-модуля, voice activity
threshold или отдельного VAD processing pipeline не найдено.

### Проверка pass / TODO / hardcode

В просмотренных production-путях screenshot, UIA, clipboard, hotkey, scratchpad,
AudioHost/recognition не найдено TODO/FIXME, mock/fake реализаций или заранее
заданных успешных результатов вместо обращения к нужному backend.
Найденные `pass` объясняются назначением:

- `tools/windows.py:124`: пустая strict-схема ClipboardGet без аргументов.
- `desktop/system_tools.py:21`: пустая strict-схема SystemInput.
- `voice/host.py:61`, `voice/local.py:95`: drain stdout при завершении helper.

Scratchpad execute возвращает нормализованные args намеренно: Runner применяет
проверенное значение в RAM после SUCCESS (`runner.py:254-256`), с лимитами 32 ключа /
32768 UTF-8 JSON bytes и очисткой при завершении. Это не заглушка сохранения.

Реальные Windows-пути используют PIL.ImageGrab, win32clipboard, UIA и
pywinauto.keyboard.send_keys. HOTKEYS allowlist, quality=65, размеры и таймауты —
явные ограничения, не фиктивные данные. Hotkey/click подтверждают dispatch операции;
бизнес-эффект приложения требует следующего наблюдения и на Mac не проверен.

## Скриншоты, provenance и лимиты

`PermissionEngine.prepare()` ограничивает **входные аргументы** действия, не tool output.
Реальный normalized screenshot payload — `{"scope":"active_window"}`, **25 UTF-8 bytes**.
Screenshot/clipboard без target допускаются `_observed_target()` как первый шаг;
изображение само по себе не становится UIA element identity или approval.
Active-window screenshot может содержать native WindowTarget metadata, по которой
Runner сопоставляет окно; это отдельно от пиксельного содержимого кадра.

Native capture ограничивает JPEG **49152 bytes**, base64 — **65536 ASCII bytes**.
PermissionEngine отделяет `image_base64` в `Outcome.screenshot_b64` после verify.
Runner держит только текущий кадр, удаляет изображение из history/UI outcomes;
после другого шага или завершения ссылка очищается. OpenAIProvider отправляет
один `input_image`, а метаданные — в untrusted_observations.

Общий бюджет OpenAIProvider — **262144 UTF-8 bytes**, включая инструкции, tool schemas,
контекст и image block. При превышении удаляются целые старые recent task-memory записи;
если этого недостаточно — context_limit до transport и чтения ключа. Текущие tool
observations/каталог не сокращаются и не обрезаются. Set-of-Marks в этом пути отсутствует.

Локальная инструментальная проверка настоящего OpenAIProvider с default transport:
Python trace останавливал выполнение непосредственно перед сетевым transport;
ключи не читались и сеть не использовалась. Для проверки размеров поля изображений
использованы синтетические base64-данные, не реальный захват Windows.

| Контекст | Размер полного JSON payload, bytes | Итог |
|---|---:|---|
| PlannerWindow, короткая команда, без наблюдений | 45179 | В бюджете |
| PlannerWindow + максимальное поле base64 | 110814 | В бюджете |
| DesktopService, короткая команда, без наблюдений | 43762 | В бюджете |
| DesktopService + максимальное поле base64 | 109397 | В бюджете |
| DesktopService + schema-valid 256 UIA элементов с 1000-символьными именами + image field | 412254 | context_limit до transport |

Последний UIA result сам имеет 292158 bytes. Ограничение 256 элементов не гарантирует
вписывание в provider budget; это воспроизведённый предел ёмкости, не Windows benchmark.
Отдельно prepare() принимает schema-valid UTF-8 payload 32030 bytes и отвергает 66030 bytes.
