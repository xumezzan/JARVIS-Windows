# План: из ассистента в кросс-приложенческого рабочего агента

Документ описывает переход от текущего Jarvis (узкий локальный ассистент: реестр
инструментов, PermissionEngine, планировщик, Outlook, браузер, Windows UIA, голос)
к агенту, который работает между 14 сервисами, держит единую память, понимает контекст,
переносит данные между приложениями, напоминает и делает сводки.

Существующее ядро не переписывается. Всё новое подключается к уже работающим
`ToolRegistry`, `PermissionEngine`, `AuditLog`, `Runner`.

## 0. Решения, которые нужно принять до кода

Текущая архитектура намеренно fail-closed. Пять инвариантов прямо мешают цели.
Каждый требует явного решения владельца; без него работа встанет посреди фазы.

| # | Инвариант сейчас | Что требуется | Предлагаемое решение |
| --- | --- | --- | --- |
| И1 | `CRITICAL` → всегда `DENY` (`permissions/policies.py:38`), в `AGENTS.md` «CRITICAL is disabled» | Отправка почты, публикация комментариев, финансовые записи | `CRITICAL` → `REQUIRE_APPROVAL` c усиленным подтверждением (ввод слова-подтверждения + отдельная запись аудита). `BLOCKED` остаётся `DENY` навсегда |
| И2 | Никаких ретраев и фолбэков | §32 промпта: retry → альтернативный путь → браузер | Ретраи только для идемпотентных SAFE-операций и для CONFIRM-операций с ключом идемпотентности. Фолбэк API→браузер — только явным шагом плана, не молча |
| И3 | Clipboard и координатные клики запрещены архитектурно | Перенос данных между приложениями без API | Clipboard как инструмент с сохранением и восстановлением прежнего содержимого. Координаты — только последний фолбэк, за отдельным флагом и подтверждением |
| И4 | Память не хранит внешние идентификаторы (`memory/models.py`) | §10: `external_ids`, связи между сервисами | Новое хранилище знаний отдельно от профиля меток. Старый профиль не трогаем — его валидаторы защищают от инъекций |
| И5 | Цель действия обязана быть наблюдена в текущей задаче (`runner.py:214`) | Длинные сценарии с переносом данных | **Инвариант сохраняем.** Знания дают только подсказку для поиска, не цель для записи. Порядок всегда: знание → поиск → наблюдение → запись |

И5 — ключевое. Именно оно отличает рабочего агента от агента, который уверенно
пишет письмо не тому человеку. Память отвечает на вопрос «где искать», а не
«куда писать».

## 1. Целевая архитектура (дельта к существующей)

```
UI (PySide6)
 └── core/composition.py        ← НОВОЕ: сборка вынесена из ui/planner_window.py
      ├── ToolRegistry           существует
      ├── PermissionEngine       существует + матрица разрешений
      ├── AuditLog               существует + workflow_id
      ├── core/workflow/         ← НОВОЕ: durable-сценарии, идемпотентность, восстановление
      ├── core/context/          ← НОВОЕ: сборка контекста под бюджет
      ├── core/providers/        ← НОВОЕ: AIProvider, OpenAI + Anthropic, роутинг
      ├── knowledge/             ← НОВОЕ: сущности, связи, разрешение имён
      └── connectors/            ← НОВОЕ: 14 сервисов по общему контракту
```

Существующие пакеты `tools/`, `browser/`, `platforms/`, `voice/`, `memory/`,
`security/`, `observability/` остаются на месте и переиспользуются.

## 2. Слой коннекторов

`connectors/base.py` — контракт:

```
class BaseConnector(Protocol):
    service: str
    def capabilities(self) -> tuple[Capability, ...]
    async def authenticate(self) -> AuthState
    async def health_check(self) -> Health
```

`Capability` описывает одну операцию: имя, риск по умолчанию, идемпотентна ли,
какие сущности читает, какие пишет. Регистрация в существующий реестр:
`register_<service>(registry, connector, matrix)` — ровно как сейчас работает
`register_outlook`, `register_browser`, `register_files`.

`connectors/http.py` — обобщение уже существующего `mail/graph.py`: транспорт
с фиксированным origin, белым списком «метод + путь», лимитом ответа, без cookies,
редиректов, прокси и ретраев. Это лучший код в репозитории; каждый новый сервис
получает его бесплатно.

Структура одного коннектора:

```
connectors/asana/
    connector.py    BaseConnector
    models.py       pydantic ToolModel-схемы
    tools.py        register_asana()
    mapping.py      результат API → сущности графа знаний
```

Правило: LLM не видит сырых HTTP-вызовов. Только семантические инструменты
(`asana.create_task`, `omadli.search_customer`).

## 3. Единая память

Новый пакет `knowledge/`, отдельная база от `memory.db`.

```
Entity
    canonical_id, type, name, aliases[]
    external_ids: {asana: "123", outlook: "john@acme.com", fireflies: "p_xyz"}
    provenance: из какого запуска и инструмента получено
    updated, confidence

Relationship
    subject → predicate → object, source_run_id
```

Типы: Person, Company, Project, Task, Meeting, Invoice, Document, Conversation,
Customer, Account.

`resolution.py` — разрешение сущностей:
- точное совпадение email или внешнего ID → связываем автоматически;
- совпадение по имени → предлагаем связь, но **спрашиваем пользователя** перед
  первым использованием в операции записи;
- уверенность и происхождение хранятся; связь можно разорвать в UI.

`context/` — сборка контекста под бюджет токенов: релевантные сущности, последние
запуски по теме, профиль меток. Никакого сброса всей базы в промпт.

Секреты в графе не хранятся никогда. Для них — `credential_ref` и 1Password.

## 4. Workflow Engine

`core/workflow/`:

- `run.py` — долгоживущий запуск в SQLite: `pending / running / waiting_approval /
  waiting_input / failed / done`, журнал шагов, возобновление после перезапуска.
- `idempotency.py` — ключ `sha256(workflow_id + step + tool + канонические аргументы)`,
  реестр выполненных эффектов, запись внешнего ID после успеха. Повтор шага, чей ключ
  уже в реестре, возвращает прежний результат и не создаёт дубль. Это закрывает §44.
- `recovery.py` — политика на каждый код ошибки: повторить / другой маршрут /
  спросить / остановиться. Состояние сценария сохраняется при любом исходе.
- `scheduler.py` — напоминания и триггеры: по времени, «после встречи»,
  «утренний дайджест».

`Runner` остаётся исполнителем одного плана. Workflow — уровень выше: он владеет
состоянием, идемпотентностью и возобновлением, и вызывает `Runner` для каждого этапа.

## 5. Разрешения

`permissions/matrix.py` — конфигурация «сервис → операция → {разрешено, риск,
подтверждение}», загружается при сборке, валидируется, дальше неизменна.

Стартовые значения:

| Сервис | Чтение | Черновик | Запись | Опасное |
| --- | --- | --- | --- | --- |
| Outlook, Teams | авто | авто | — | отправка: подтверждение |
| Calendar | авто | авто | создание: подтверждение | отмена встречи: подтверждение |
| Asana, Notion | авто | авто | создание/правка: авто (настраивается) | удаление: подтверждение |
| Fireflies, Loom | авто | — | — | — |
| QuickBooks | авто | — | запрещено в фазе 1 | транзакции: усиленное подтверждение |
| AWS | авто (read-only роль) | — | запрещено | любая запись: усиленное подтверждение |
| Instagram, Facebook | авто | авто | — | публикация: подтверждение |
| M365 Admin | авто | — | запрещено | любая запись: усиленное подтверждение |
| 1Password | только по `credential_ref` | — | — | выдача секрета в UI: подтверждение |
| Omadli | авто | авто | по результатам разведки | удаление: подтверждение |

Автономный режим (уже есть в UI) продолжает заменять пошаговое подтверждение,
но не действует на усиленные подтверждения.

## 6. Провайдеры моделей и Claude

`core/providers/base.py` — `AIProvider` с профилями задач: `fast`, `strong`, `vision`.
Существующий `openai_provider.py` переезжает туда без изменения поведения.
Добавляется `anthropic.py`.

Claude участвует дважды:
- как альтернативный оркестратор (выбирается в настройках);
- как инструмент `claude.analyze` для разбора документа, транскрипта, кода —
  когда основная модель решает, что нужен отдельный сильный разбор.

Роутинг: классификация намерения и извлечение — дешёвая модель; планирование
кросс-приложенческого сценария и разбор UI — сильная; скриншоты — vision.

## 7. Перенос данных между приложениями

Приоритет неизменен: API → браузер → GUI.

Новое:
- `tools/clipboard.py`: `clipboard.read` (SAFE), `clipboard.write` (CONFIRM).
  Прежнее содержимое сохраняется и восстанавливается после операции.
- `windows.invoke_element` — нажатие по элементу UIA, не по координатам.
- `windows.screenshot` (SAFE) — для vision-разбора незнакомого интерфейса.
- Браузер: загрузка и скачивание файлов, переключение вкладок.

Буфер обмена — всегда фолбэк. Если между двумя сервисами есть API, агент обязан
идти через API; это проверяется тестом, а не соглашением.

## 8. Отчёты, сводки, напоминания

`core/report/`:
- «Что у меня сегодня» — Calendar + Asana + Teams + Outlook + Fireflies в один ответ.
- Follow-up по встрече — резюме, решения, задачи, сроки → страница Notion + задачи Asana.
- Дайджест по расписанию — утром, голосом и на экране.

Сводка собирается из фактических результатов инструментов с указанием источника
каждого пункта. Модель формулирует текст, но не придумывает факты: каждая строка
отчёта ссылается на сущность или на шаг запуска.

## 9. UI

- Живое исполнение: чеклист шагов (готово / текущий / ожидает), а не полоса загрузки.
  Протокол `notify()` в `Runner` уже даёт нужные события.
- Новые разделы: «Запуски» (история и возобновление), «Знания» (сущности и связи),
  «Подключения» (коннекторы, здоровье, переподключение), «Активность» (аудит),
  «Настройки» (матрица разрешений).
- Очередь подтверждений: в автономном запуске подтверждения копятся и показываются
  пачкой, с возможностью отклонить отдельный пункт.
- Минимализм главного экрана сохраняется: орб, голос, текущая задача.

## 13. Ворота качества

Без изменений к текущим правилам репозитория, плюс для каждого коннектора:
модульные тесты, тесты на отказ аутентификации, таймаут, ретрай, дубль.

### Как граф знаний сохраняет инвариант И5

Хранилище держит внешние идентификаторы — иначе связать Джона в Outlook и Джона в Asana
невозможно. Но проекция для планировщика (`Hint`) отдаёт только имя, псевдонимы и
**названия сервисов**, где сущность известна, и никогда сам идентификатор. Модель не может
скопировать в аргумент инструмента то, чего не видела в текущей задаче. Порядок остаётся:
знание подсказывает, где искать → поиск возвращает наблюдение → запись идёт по наблюдению.

Слияние идёт только по идентификаторам. Совпадение имени — вопрос владельцу, а не решение:
двух разных Джонов нельзя склеивать по строке. Каждый идентификатор помнит инструмент и
запуск, которые его наблюдали, и принадлежит ровно одной сущности.

### Как закрыт §44 (идемпотентность)

Шаг записывается в журнал дважды: до вызова инструмента и после получения результата.
Порядок именно такой, потому что опасен как раз случай, когда сервис принял работу, а ответ
не дошёл. Шаг, оставшийся в состоянии `issued`, считается возможно выполненным, и повторная
попытка отказывается его повторять, а не предполагает, что ничего не произошло.

Ключ шага — хеш имени инструмента и канонических аргументов, поэтому один и тот же эффект
опознаётся даже если план вокруг него изменился. Журнал хранит только идентичность и исход:
ни аргументов, ни результатов, ни адресатов — то же правило, что у журнала аудита.

Восстановление (`recovery.py`) подчинено двум правилам, которые идут раньше любых категорий:
шаг, который мог дойти до сервиса, не повторяется автоматически никогда, и шаг неидемпотентного
инструмента — тоже. Таймаут не является доказательством, что ничего не случилось.

### Как отбирается контекст

Отбор детерминированный: одна и та же команда и один и тот же граф всегда дают один и тот
же набор. Никакого второго обращения к модели перед первым. Совпадение пословное, а не по
подстроке, поэтому «John» не претендует на «Johnson»; более короткое слово совпадает с
длинным только как префикс от четырёх символов — этого хватает на русские падежи
(«Джон» в «Джона», «проект» в «проекта») и не хватает на случайные совпадения.

Сущность, не набравшая ни одного очка, в контекст не попадает вообще. Бюджет — жёсткий
предел в символах, а не оценка: лишнее отбрасывается с хвоста ранжирования, поэтому
остаются самые сильные совпадения.

Контекст — подспорье, а не предусловие: нечитаемый граф оставляет планировщику меньше
данных, но не останавливает запрос пользователя. Чтение графа, которого ещё нет, не
создаёт базу на диске.

### Согласие на передачу контекста

Знакомые лица и проекты — это персональные данные, поэтому они подчинены тому же
одноразовому согласию во вкладке «Память», что и выбранные метки. Формулировка флажка
расширена, чтобы описывать и то и другое. Перед запуском окно печатает, кого именно оно
взяло с собой, — контекст не уезжает незаметно.

Ворота на момент записи: 599 тестов пройдено, 6 пропущено (требуют реального
оборудования или opt-in), Ruff, `ruff format` и mypy strict чистые,
`python -m jarvis --smoke-test` — success.

### Известный дефект: аварийное завершение под нагрузкой

При загруженной машине (полный прогон занимает 60–66с вместо 44с) набор тестов
воспроизводимо падает с `Fatal Python error: Aborted`. Сигнатура одинакова: рабочий поток
почтовой панели находится внутри `AuditLog.write`, главный поток — в `MemoryPanel._done`.
Реже вместо падения процесса отваливаются тесты `test_voice_ui.py` по таймауту ожидания.

Измерено: **6 падений из 8 прогонов на коммите `cd42c2c`**, то есть до появления
`core/context/`. На быстрой машине — 0 из 5 на том же коммите. Дефект существует
независимо от платформенных изменений и относится к жизненному циклу Qt-потоков в
`ui/mail_panel.py` и `ui/memory_panel.py`. Требует отдельной задачи.
