# План 0.2–0.3 — проактивный ассистент с постоянным голосом

Цель этапа: ассистент, который помнит контекст владельца, сам замечает повод для
действия, работает с широким кругом сервисов и слышит обращение без удержания кнопки —
**не ослабляя контракт подтверждения**. Ни один пункт этого плана не имеет права выдать
`ApprovalToken` без явного UI-события владельца.

Предусловие для всего документа: **этап 9 закрыт** (native-установка, живой Outlook OAuth,
реальный микрофон). До этого ни одна фаза ниже не начинается — иначе новые слои
строятся на непроверенном исполнении.

## Что уже есть и переиспользуется

| Нужно для цели | Где уже лежит |
|---|---|
| Долговечные запуски, идемпотентность, восстановление | `core/workflow/` (`journal.py`, `store.py`, `recovery.py`) |
| Память владельца (явные метки) | `memory/` |
| Наблюдённые сущности и склейка личности между сервисами | `knowledge/` |
| Отбор контекста под бюджет | `core/context/assembly.py`, `relevance.py` |
| Контракт коннектора и общий HTTP-транспорт | `connectors/base.py`, `connectors/http.py` |
| Выбор модели с эскалацией по факту | `core/planner/routing.py` |
| Запись фразы с окончанием по тишине | `voice/contracts.py` — `Recorder.record(..., listen=True)` |
| Голосовая отмена | `Transcript.is_cancel` |

Ключевой вывод: три из четырёх целей — это **надстройки над существующими швами**, а не
новые подсистемы. Отдельной разработки с нуля требует только wake-word.

---

## Фаза B — Проактивность (`core/routines/`)

Самая важная фаза: она меняет характер продукта с «инструмента» на «ассистента».

### Главное проектное решение

Проактивность **не равна** самостоятельному исполнению. Иначе она сталкивается с
требованием AGENTS.md: подтверждение приходит только из проверенного UI-события.
Поэтому рутина разделена надвое:

1. **Наблюдение** — запуск только SAFE / read-only инструментов. Может идти без владельца.
2. **Предложение** — если наблюдение нашло повод, рутина кладёт в очередь *предложение*
   с уже собранным снимком действия. Снимок показывается владельцу; одобрение в UI
   создаёт токен ровно так же, как сегодня.

**Рутина никогда не создаёт `ApprovalToken`.** Это единственное неотменяемое правило фазы.

### Состав работ

- `core/routines/triggers.py` — расписание (cron-подобное) и опрос коннектора
  (новое письмо по фильтру, встреча через N минут). Наблюдение за файловой системой
  в 0.2 не входит: слишком шумный источник.
- `core/routines/runner.py` — исполняет наблюдение как обычный run: свой `run_id`,
  журнал, ключи идемпотентности. Переиспользует `core/workflow/` целиком.
- `core/routines/proposals.py` — очередь предложений с TTL. Просроченное предложение
  исчезает, а не ждёт вечно: повод устаревает.
- `ui/` — панель предложений; каждое раскрывается в тот же экран подтверждения.

### Ограничения, без которых фазу нельзя выпускать

- Рутина **прибита к быстрой модели без эскалации**. Фоновый запуск, который сам уходит
  на сильную модель в цикле, — это неожиданный счёт. `EscalatingRouter` в фоне не участвует.
- Бюджет на сутки: число запусков и вызовов модели, при исчерпании — стоп с записью в журнал.
- Каждая рутина включается отдельно, выключается одним переключателем, и есть общий kill switch.
- **Тишина по умолчанию.** Рутина, не нашедшая повода, не производит ни одного уведомления.
  Иначе ассистент становится шумом и его выключают — это главный риск провала фазы, не технический.

### Ворота качества

Рутина без владельца за клавиатурой не исполняет ничего вне SAFE; предложение с истёкшим
TTL не подтверждается; изменение данных между наблюдением и подтверждением инвалидирует
снимок; исчерпание дневного бюджета останавливает рутину; повторный запуск после
перезапуска процесса не дублирует уже выданный эффект.

## Фаза C — Память, которая накапливается

Идёт параллельно с B: другие модули, пересечение только в `core/context/assembly.py`.

### Чего не хватает

`memory/` — что владелец напечатал. `knowledge/` — что увидели коннекторы. Нет третьего:
**что ассистент выучил из завершённых запусков самого владельца**. Из-за этого каждый раз
заново уточняется, какое приложение имеется в виду под «почтой» и какой Джон имеется в виду.

### Важное ограничение источника

Аудит-лог намеренно без полезной нагрузки, журнал хранит идентичность и исход, но не
аргументы. Это правило остаётся. Значит **выводимую память нельзя намайнить из логов** —
её пишет отдельный слой с явного согласия.

### Состав работ

- `memory/derived.py` — сопоставления, а не содержимое: фраза → инструмент,
  псевдоним → `entity_id`, «почта» → конкретное приложение.
- Запись только из запуска, который завершился успешно и был подтверждён владельцем.
- Подтверждение совпадения по имени из `knowledge/resolution.py` **сохраняется**:
  сегодня владелец подтверждает «тот самый Джон» заново, дальше это должно жить.
- Каждая выведенная запись видна в панели памяти, удаляется поштучно, имеет TTL.
- Третий источник в `core/context/assembly.py` под тем же жёстким бюджетом.

### Ворота качества

Незавершённый или неподтверждённый запуск не пишет ничего; в выведенной памяти
не появляется ни содержимого, ни идентификаторов в контексте планировщика; удаление
записи владельцем немедленно меняет следующий отбор контекста; бюджет сборки не превышен
при заполненных всех трёх источниках.

## Фаза D — Широта охвата через MCP (`connectors/mcp.py`)

### Состав работ

Клиент MCP, который читает список инструментов внешнего сервера и отображает каждый
в `Capability` существующего контракта. Дальше всё как у своих коннекторов: регистрация
как типизированный инструмент, исполнение через `PermissionEngine`.

### Главная сложность — и осознанная цена

`connectors/base.py` требует: метаданные capability — доверенный код, никогда не значение
от модели, ответа сервиса или аргумента. Самоописание MCP-сервера — ровно значение от сервиса.

Отсюда: **инструмент MCP не назначает себе риск.** Сервер приходит как манифест, владелец
один раз проходит его в UI и проставляет риск по каждому инструменту. Непроверенный
инструмент — `BLOCKED`. Манифест закрепляется хешем; сервер, изменивший набор инструментов,
возвращается на проверку.

Это трение, которого нет у OpenClaw. Его нужно принять сознательно: оно и есть плата за то,
что у вас подтверждение привязано к снимку, а не к сессии.

### Ворота качества

Инструмент вне проверенного манифеста не исполняется; изменение манифеста сбрасывает
проверку; ответ MCP-сервера не может повысить собственные права и не становится
инструкцией; отказ сервера не роняет задачу владельца.

## Фаза A — Голос без кнопки (`voice/wake.py`)

Идёт последней: самое чувствительное к приватности изменение, и его нельзя выпускать
поверх непроверенного остального.

### Состав работ

- `Wake` — протокол рядом с `Recorder` / `Recognizer` / `Speaker`. Он **не расшифровывает**,
  а только решает, что следующая фраза адресована ассистенту. Локальная CPU-модель
  (openWakeWord / Porcupine), без облака.
- Срабатывание → уже существующий `record(listen=True)`, который завершает фразу по тишине.
  Дальше — тот же конвейер. Новая поверхность минимальна.
- Кольцевой буфер не покидает процесс, аудио не сохраняется на диск.
- Постоянный видимый индикатор, когда слушатель взведён, — требование AGENTS.md о запрете
  скрытой записи микрофона относится и к ожиданию слова активации.

### Что становится важнее без кнопки

Голосовая отмена (`Transcript.is_cancel`) из удобства превращается в основной способ
остановки: кнопки под рукой нет. Слова отмены должны распознаваться и во время активного
запуска, а не только между ними.

### Ложное срабатывание

Смягчается архитектурой, а не только качеством модели: срабатывание лишь открывает запись,
а результат идёт через тот же планировщик и тот же CONFIRM. Ложное «Джарвис» не может
отправить письмо. Это следствие модели безопасности — здесь она окупается.

### Ворота качества

Частота ложных срабатываний за час обычной речи и фонового звука; поведение при
срабатывании во время активного запуска; отмена голосом во время исполнения;
отсутствие аудио на диске после сбоя процесса; видимость индикатора во всех состояниях.

## Порядок и почему такой

```
Этап 9  →  B (рутины)  ‖  C (память)  →  D (MCP)  →  A (wake word)
```

- **B первой**: она одна меняет характер продукта, и делается поверх уже готового
  `core/workflow/`. Outlook и календаря достаточно, чтобы рутины были полезны сразу.
- **C параллельно B**: другие модули, малый объём, улучшает качество всех остальных фаз.
- **D после B**: очередь предложений уже существует, и широта охвата сразу её наполняет.
  Наоборот — хуже: много сервисов без проактивности дают только больше ручных команд.
- **A последней**: наибольший риск приватности и наименьшая функциональная отдача
  на единицу работы. Постоянный голос поверх недоделанных рутин — это громкий недоделанный
  ассистент.

## Что в этот этап не входит

Мультимодальность (чтение экрана моделью) и каналы вне машины (мессенджер как второй UI).
Оба осмысленны, оба крупные, оба зависят от того, что фазы выше закрыты. Не начинать раньше.
