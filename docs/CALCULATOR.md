# Открыть калькулятор и ввести цифру

Команда владельца: **«открой калькулятор и набери 1»**. В офлайн-режиме она должна
открыть настоящий Microsoft Calculator, ввести цифру и проверить её на дисплее.
Это исправление конкретного сценария; общая настольная автоматизация из фаз 3–4
плана агента этим не объявляется реализованной.

Прежний офлайн-провайдер передавал `калькулятор и набери 1` целиком в `windows.open_app`.
Windows искала приложение с этим названием и возвращала `application_missing`, хотя
обычная команда «открой калькулятор» работала. Теперь составной рецепт отделяет имя
приложения от действия. Неизвестные цепочки с «и набери/введи/нажми» вызывают уточнение,
а не поиск приложения с названием всей фразы.

## Поддерживаемый сценарий

- «открой калькулятор и набери 1»; вместо «набери» также «введи», «напиши»,
  «напечатай» или «нажми»; вместо «открой» также «открыть», «запусти», «запустить».
- Название: «калькулятор», `calculator`, `calc`. Вводится одна цифра 0–9.
- Microsoft Calculator из защищённого пакета WindowsApps, обычный режим, дисплей 0,
  без незавершённого выражения. Уже набранное число или выражение остаётся на месте:
  неподходящее или изменившееся состояние отклоняется, Clear/Equals не нажимаются.

## Исполнение и подтверждение

1. `windows.open_app` возвращает наблюдаемую идентичность окна.
2. SAFE `windows.get_calculator_digit` наблюдает выбранную цифровую кнопку,
   дисплей и выражение. Учтён ApplicationFrameHost: отдельно проверяются PID,
   время запуска и путь настоящего CalculatorApp.exe, которому принадлежат контролы.
3. `windows.calculator_digit` имеет уровень CONFIRM. Как и другие действия,
   проходит PermissionEngine, точный snapshot, UI approval authority, аудит,
   журнал эффекта и защиту от повтора. Существующий явный автономный режим UI
   сохраняет свой обычный порядок выдачи approval; инструмент не получает authority.
4. Перед одним UIA Invoke повторно проверяются окно, процесс, runtime id,
   automation id, роль, класс, имя и видимость контролов, дисплей и выражение.
   Затем читается результат; отдельный verifier вновь проверяет дисплей.

Нет глобальных клавиш, координат, буфера обмена, универсального селектора или
произвольного командного текста. Caller не может передать Equals, Clear или
кнопку другого приложения. Runner требует наблюдение кнопки в той же задаче.
Обычная симуляция не вызывает адаптер; неизвестное после прерывания действие
не повторяется автоматически. Новый инструмент не имеет голосового approval.

## Проверка

Регрессии покрывают составной разбор, привязку кнопки к наблюдению, отсутствие
эффектов без approval и при симуляции, независимый read-back, отказ при смене
процесса/кнопки/режима/выражения/дисплея, чужой пакет и повторное исполнение.
Пустое выражение настоящего Calculator скрыто; его identity и visibility также
сохраняются и сверяются.

Живая проверка выполняется отдельно в установленном приложении: ввести исходную
команду в Jarvis, дождаться завершения, проверить `windows.calculator_digit: SUCCESS`
и настоящую цифру 1 в окне калькулятора. Fixture-результаты не заменяют этот прогон.

Локальные проверки 16.10.2026, Windows 11 x64, Python 3.13.15, отдельная
`.venv-acceptance`: полный pytest **1116 passed, 7 skipped**; native Windows Qt
integration **202 passed**; Ruff check/format, mypy (255 файлов), pip check, GUI smoke
и wheel/sdist build пройдены. Команды Python запускались с `-I -X utf8`, чтобы
UTF-8 отчётов читался так же, как в CI с `PYTHONUTF8=1`. Первый прогон без `-X utf8`
обнаружил четыре существующих чтения тестовых UTF-8 отчётов в cp1251; тесты и проверки
не отключались. Во время native Qt был выведен уже описанный в WINDOWS_ACCEPTANCE
COM diagnostic `0x8001010d`; процесс продолжил работу и завершился кодом 0.
