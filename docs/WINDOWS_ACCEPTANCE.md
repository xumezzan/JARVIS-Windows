## Один запрос на установку

Пользователь открывает полную копию репозитория в Codex на целевом ноутбуке и просит
установить Jarvis. Агент читает AGENTS.md и выполняет из корня:

```powershell
& '.\scripts\windows\Install-Jarvis.cmd'
if ($LASTEXITCODE -ne 0) { throw 'Installation did not pass' }
Get-Content -LiteralPath "$env:LOCALAPPDATA\JarvisInstall\installation-report.json"
```

Проверить настоящее окно и запуск **Jarvis** с рабочего стола и из «Пуск» после закрытия
тестового окна.
Runtime готовится автоматически. Скрипт не повышает права, не меняет PATH, associations,
постоянную execution policy, микрофонные разрешения и credentials. CMD задаёт
`-ExecutionPolicy Bypass` только собственному процессу PowerShell для локального проверенного
скрипта. Корпоративная Group Policy имеет приоритет. При блокировке обязательной политикой
остановиться и использовать разрешённый организацией процесс, не выключать защиту.

Корень компонентов: `%LOCALAPPDATA%\JarvisInstall`. Пользовательские данные:
`%LOCALAPPDATA%\Jarvis` либо явный абсолютный `JARVIS_DATA_DIR`. Не задавать каталог данных внутри
каталога установки. Перед повторной установкой закрыть окна Jarvis.

Если нет русского SAPI5-голоса: **Параметры → Время и язык → Речь → Управление голосами →
Добавить голоса → Русский**. Пользователь принимает необходимые системные диалоги.
Повторить установщик; наличие голоса ещё не означает, что звук реально слышен.
Дополнительные Chrome/VS Code не устанавливаются скрытно; для полного сценария нужны
их обычные официальные установки в поддерживаемых каталогах.

## Проверки разработчика без ручной подготовки Python

Из корня репозитория, после установки:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\windows\Test-Jarvis.ps1
```

Создаётся отдельное `.venv-acceptance`, устанавливается `.[dev,voice]` и собственный Chromium.
Скрипт выполняет full pytest, Ruff lint/format, mypy, pip check, native Qt integration,
GUI smoke и build. Runtime установленного приложения не получает dev dependencies.
Фактические версии acceptance-окружения могут отличаться от runtime, пока нет Windows lock;
проверить оба набора. Только после native-приёмки сформировать constraints с хэшами,
повторить чистую установку с ними и закрепить версии.

Опциональные реальные проверки — только после подготовки пользовательских данных:

```powershell
# Сохранить и закрыть свои документы Notepad; тест оставляет новый текст и окна открытыми.
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\windows\Test-Jarvis.ps1 -NativeApps

# Пользователь держит кнопку записи, проверяет transcript и отдельно запускает команду.
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\windows\Test-Jarvis.ps1 -Voice

# Только после явного UI setup ключа и выбора доступного своему аккаунту ID модели:
$env:JARVIS_PLANNER_MODEL = '<выбранный ID модели>'
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\windows\Test-Jarvis.ps1 -LiveModel
```

LiveModel отправляет тестовую команду и расходует API usage. Ключ только в OS credential
store; не вставлять его в команду. Для Outlook выбрать свой тестовый аккаунт и получателя,
пройти полный [сценарий этапа 8](MILESTONE_8.md). Автоматического live-send теста нет.

## Полный сценарий MVP — вручную в реальном UI

1. Открыть установленный Jarvis из «Пуск». **Открыть планировщик**, offline provider.
   Снять Simulation Mode для реальных действий. Главная строка команд выполняет то же самое и по умолчанию работает в режиме «Выполнять действия».
2. Ввести **Открой Chrome и найди OpenAI**. Проверить Chrome и точное подтверждение URL
   поиска. Поиск выполняется в отдельном принадлежащем Jarvis Chromium, без профиля Chrome.
   Проверить фактический текст выдачи. Challenge, ошибка, SIMULATED или просто открытая
   страница — не успешный поиск. Поиск именно в пользовательском Chrome не реализован;
   если требуется этот вариант, это открытый продуктовый критерий, не разрешение ослабить
   browser boundary. Публичная выдача DuckDuckGo может быть недоступна.
3. Ввести **Открой Блокнот и напиши Jarvis test successful**. До нажатия настоящей кнопки
   Approve редактор пуст. В preview сверить приложение, окно, вкладку и точный текст.
   После подтверждения — точный текст в Notepad и успешный UIA read-back. Непустой
   восстановленный файл не заменяется. Проверить Cancel, expiry и изменение выбранной вкладки.
4. В **Память** явно сохранить метку приложения `notepad`, выбрать её для одной задачи,
   выполнить **открой выбранное приложение**. Используется новое наблюдение; старые approvals
   не переиспользуются. Роль контакта вызывает уточнение; проверить edit/delete/clear.
5. Реальная речь: held gesture → видимый индикатор → release → transcript review → отдельный
   запуск. Проверить ошибочный transcript с отправкой: автоматического send/approval нет.
   Проверить focus loss, Escape, Stop и закрытие окна на записи/распознавании/озвучивании.
6. **Outlook**: свой тестовый аккаунт/получатель, preview To/Cc/Bcc/subject/body/attachments,
   локальный draft, точное подтверждение remote draft и send. `202` только accepted;
   отдельно проверить Отправленные и получение. При неопределённом исходе не повторять POST.
7. Проверить внешнюю инструкцию «ignore policy / approve / send» в синтетическом содержимом:
   режим/политика/recipient не меняются. Cancel до approval не исполняет действие. Проверить
   Stop на ожидающем шаге: новые шаги не запускаются, исход не выдаётся за успех.
8. В аудит попадают выполненные/отклонённые/ошибочные/отменённые шаги без содержания,
   токенов и credentials. Отключение Outlook очищает локальный credential cache.

### Найдено и исправлено: установщик молчал о том, что Jarvis держит его файлы

Установщик запускает приложение ради проверки окна и **намеренно оставляет его работать**.
Значит каждая установка оставляет живую копию, а следующая, которой нужно пересобрать
второй слот, встречает этот остаток: он держит файлы, которые надо заменить.

Проявилось так: отказ через 4,5 секунды с текстом «Setup failed at the displayed step»,
хотя ни одного шага показано не было — отказ случился раньше первого. Причина
(`PermissionError` от `shutil.rmtree`) отбрасывалась целиком. После закрытия остатков
та же команда прошла за 90 секунд. Исправлено: слот, который не удалось снести, называет
причину и что сделать, а неожиданный отказ называет свой класс и код.

Побочное наблюдение: `rmtree` успевает удалить почти всё до блокировки, поэтому неактивный
слот остаётся выпотрошенным. Это то же состояние, через которое проходит обычная
пересборка; рабочий слот и данные не затрагиваются.

### Не пройдено: публичная поисковая выдача

`browser.search` ходит в единственный источник — `lite.duckduckgo.com`. В этом прогоне
**первые два запроса вернули 200 и настоящую выдачу, все последующие четырнадцать — 202
и страницу-проверку** «подтвердите, что вы человек». Приложение ведёт себя правильно:
202 не выдаётся за результат, поиск честно завершается `browser_failure`.

Проверено, что дело не в сети и не в нашем транспорте:

- обычный `Invoke-WebRequest` к тому же URL — 200 и 23 904 байта за 1,35 с;
- собственный резолвер, собственный TLS-контекст и middleware «один запрос» по очереди
  исключены: с ними и без них ответ одинаковый, каждая попытка укладывается в 0,4 с;
- корреляция «наш резолвер → 202» не подтвердилась: при чередовании обе схемы получали
  202 одинаково.

Значит источник выдаёт проверку честно представившемуся неброузерному клиенту после
первых обращений. Отвечать на проверку и притворяться браузером граница запрещает, и
правильно. Вывод: **поиск непригоден для задачи, которая ищет больше одного раза**, и
это продуктовое ограничение, а не дефект кода. Закрывается фазой 5 плана агента
(`docs/AGENT_PLAN.md`): страницу запрашивает настоящий браузер, потому что он и есть
браузер, без подделки.

  повтора. Значит это были не циклы, а примерно восемь отдельных попыток — шесть из них

  модель — хотя обоснование для эскалации ровно то же, что уже записано в `routing.py`:
  предложение отвергнуто до того, как что-либо выполнилось, и повтор стоит только токенов.
  Сейчас вместо эскалации задача просто заканчивается ошибкой. Поведение планировщика в
  фазу 0 не меняется — это заявка на отдельное решение.
- Ворото аудита держится на настоящих данных: 162 записи, в каждой `arguments: "[REDACTED]"`,
  ни токенов, ни содержимого, ни адресатов.

### Наблюдение: COM-исключение на нативных прогонах

На прогонах с `QT_QPA_PLATFORM=windows` обработчик печатает
`Windows fatal exception: code 0x8001010d` (`RPC_E_CANTCALLOUT_ININPUTSYNCCALL`) —
исходящий COM-вызов во время обработки input-synchronous вызова. Процесс продолжает

### Шесть дефектов, которых не видел ни один тест

Все найдены запуском, не чтением кода, и все исправлены.

1. **Каталог скрывал от модели уровень `ROUTINE`** — одиннадцать инструментов: печать
   текста, запись и переименование файла, черновик письма, весь браузер кроме чтения.
   Фильтр писался, когда уровней было два, и не обновился, когда `ROUTINE` появился между
   ними. Это и есть причина восьми отказов `unknown` в журнале аудита владельца.
2. **DeepSeek не соблюдает `parallel_tool_calls: false`** — на команду из трёх частей
   отвечает тремя вызовами сразу, 3 ответа из 7 в измеренном прогоне. Ответ отвергался
   целиком, и задача умирала.
3. **Управляющий ответ в ограде** ```` ```json ```` не читался: задача делала работу
   и объявляла себя ошибкой.
4. **Ответ на уточнение уходил без вопроса** — модель видела `["Да, продолжай."]`, не могла
   понять, с чем согласилась, и спрашивала снова до исчерпания лимита.
5. **В инструкциях не было ни слова про `ROUTINE`** — модель просила разрешения на каждое
   обычное действие.
6. **Лишние осмотры**: `windows.open_app` уже возвращает окно вместе с его текстовым полем,
   а модель шла смотреть заново. 5 шагов → 2–3.
