# План: персональный компьютерный агент

Это действующий план продукта. Он заменяет ту часть [AMBIENT_PLAN.md](AMBIENT_PLAN.md) и
[PLATFORM_PLAN.md](PLATFORM_PLAN.md), которая смотрела вперёд; сделанное по ним остаётся
в силе и описано там как история решений.

## Цель

Владелец ставит **цель**, а не команду. Он говорит не «что нажать», а «что сделать»:

> «Джарвис, подготовь всё необходимое к сегодняшней встрече с клиентом».
> «Джарвис, подготовь отчёт по моей работе за эту неделю и отправь его руководителю».

Дальше решает сам агент: какие программы открыть, какие данные достать, где их искать,
как связать одно с другим, как обработать, что подготовить, где остановиться и о чём
спросить. Обычную работу он делает молча; владельца он трогает там, где ошибка дорога
или необратима.

Это не чат-бот и не набор макросов. Это цифровой сотрудник, который работает за
компьютером примерно так, как это делает человек.

## Правила, которые не меняются

1. **API вперёд рук.** Есть у сервиса API или MCP — идём туда: надёжнее и быстрее клика.
   Нет — смотрим на экран и работаем мышью и клавиатурой. Порядок предпочтения всегда:
   API → браузер → графический интерфейс. Это проверяется тестом, а не соглашением.
2. **Свобода на обычной работе.** Открыть приложение, перейти на страницу, кликнуть,
   напечатать, сохранить черновик — без вопросов.
3. **Стоп перед дорогим.** Отправка письма, публикация, удаление, деньги, изменение
   важных настроек — точный снимок действия, показанный владельцу, и подтверждение
   ровно перед выполнением.
4. **Ответ сервиса — данные, а не приказ.** Текст письма, содержимое страницы, ответ
   MCP-сервера и то, что видно на экране, никогда не становятся именем инструмента,
   аргументом или разрешением.
5. **Цель записи наблюдается в текущей задаче** (инвариант И5). Память говорит, где
   искать, а не куда писать. Порядок всегда: знание → поиск → наблюдение → запись.

### Вывод сверки

Совпадает по существу: разрешения, память, коннекторы, голосовой ввод, выбор модели,
орб. Это прочный низ, и переписывать его не нужно.

Не совпадает: **глаза, руки и настоящий браузер**. Длина задачи закрыта фазой 1; без
остальных трёх агент по-прежнему умеет только то, что делается через API.

## Шесть решений владельца — приняты 17.09.2026

Архитектура намеренно закрыта наглухо. Пять запретов прямо мешали цели, и каждый —
осознанный, а не случайный. Снять их мог только владелец, и **17.09.2026 он принял
все шесть предложенных решений целиком**. Колонка «предлагаемое решение» — теперь
действующее правило; границы, на которых оно держится, записаны в `AGENTS.md` и
[SECURITY.md](SECURITY.md).

Принятое решение — это разрешение проектировать, а не разрешение исполнять: пока
фаза не написана и не проверена, соответствующей способности у ассистента нет.
`CRITICAL` остаётся выключенным до того, как усиленное подтверждение будет
реализовано, а не до того, как решение принято.

| # | Как сейчас | Что требуется | Предлагаемое решение |
| --- | --- | --- | --- |
| Р1 | Снимка экрана не существует; `AGENTS.md` запрещает координатную автоматизацию | «Читать содержимое экрана, распознавать элементы интерфейса» | Снимок экрана — наблюдение уровня `SAFE`, только окно целевого приложения, никогда весь рабочий стол молча. Поле пароля не снимается. Снимок — данные: он не выдаёт разрешений и не становится аргументом |
| Р2 | Есть только печать в наблюдённое поле | «Нажимать кнопки, перемещать мышь, копировать и вставлять» | `invoke_element` по элементу дерева интерфейса, а не по координатам; ограниченный набор клавиш; буфер обмена с сохранением и возвратом прежнего содержимого. Всё — `ROUTINE`. Координаты — последний фолбэк, за отдельным флагом и подтверждением |
| Р3 | Браузер без JavaScript, без POST, без профиля | «Открывать браузер и вкладки», работать с веб-сервисами | Собственный **постоянный** профиль браузера с включённым JavaScript. Вход в сервисы выполняет владелец руками в этом окне; агент никогда не вводит пароли. POST классифицируется по действию, а не запрещён целиком |
| Р4 | 8 действий, 180 секунд, задача умирает вместе с окном | Многошаговая работа между программами | Потолки поднимаются до 64 шагов и часа, но **не на доверии**: длинная задача идёт как durable-запуск `core/workflow/` с журналом, ключами идемпотентности и возобновлением после перезапуска |
| Р5 | `CRITICAL` → всегда запрет | «Финансовые операции… требуют моего подтверждения» | `CRITICAL` → усиленное подтверждение: владелец произносит или вводит контрольную деталь снимка, отдельная запись аудита, никакой автономии и никакого голосового «да». `BLOCKED` остаётся запретом навсегда |
| Р6 | В облако уходит текст команды, наблюдения и выбранные метки | Модель, которая смотрит на экран | Снимок экрана в облако — **отдельное согласие, отдельно от текстового**, с именем получателя и на одну задачу. Локальный разбор дерева интерфейса пробуется первым и в облако не уходит |

Р1–Р3 и Р6 — это разворот прежних инвариантов И3 и правила «мультимодальность не
входит». Разворот осознанный: они писались под узкого ассистента, а продукт другой.
Инвариант И5 развороту не подлежал и не развёрнут: цель записи по-прежнему должна
быть наблюдена в текущей задаче, и ни экран, ни память этого не заменяют.

## Фазы

Оценки — для сфокусированной работы, без ожидания внешних одобрений.

### Фаза 0 — Реальность (открыта, блокирует всё)

Пока ассистент не установлен и не запущен на целевой Windows, каждая фаза ниже
строится на непроверенном исполнении.

1. Установка на чистую Windows 11 одним запросом; отчёт установщика и живое окно.
2. Настоящий микрофон: слово активации, запись, распознавание, голосовое подтверждение.
3. Живой Outlook: OAuth, чтение, черновик, отправка с точным подтверждением.
4. Живой DeepSeek как основной провайдер обычной работы.

Выход: заполненная матрица [WINDOWS_ACCEPTANCE.md](WINDOWS_ACCEPTANCE.md).

### Фаза 1 — Длинная задача (1,5 недели)

Самое дешёвое из недостающего и самое заметное: без него агент обрывается на середине
любого настоящего поручения.

- `Limits` растут до 64 шагов и 3600 секунд, но задача теперь **владеет** запуском
  `core/workflow/`: журнал шагов, ключ идемпотентности на каждый эффект, состояния
  `running / waiting_approval / waiting_input / failed / done`.
- Возобновление: закрытое окно и перезапуск процесса не теряют задачу. Шаг, оставшийся
  в состоянии `issued`, считается возможно выполненным и не повторяется автоматически.
- Живой чеклист в UI: сделано / идёт / ждёт — вместо полосы загрузки. Протокол
  `notify()` в `Runner` уже даёт нужные события.
- Очередь подтверждений: пока агент работает, накопившееся дорогое показывается пачкой,
  каждый пункт отклоняется отдельно.
- Бюджет запуска: число вызовов модели и потолок стоимости на задачу, видимые владельцу.

Ворота: задача из тридцати шагов доходит до конца; перезапуск посреди неё не теряет
и не дублирует ни одного эффекта; отмена останавливает следующий шаг, а не делает вид,
что предыдущего не было; исчерпание бюджета останавливает задачу с честным отчётом.

#### Состояние на 17.09.2026: ядро сделано, поверхность нет

Почему фаза 1 пошла раньше, чем закрылась фаза 0: целевой Windows-ноутбук владельцу сейчас
недоступен, а ядро длинной задачи платформы не касается — это планировщик, журнал и
SQLite. Порядок фаз при этом не отменён. Ничто из написанного не считается проверенным,
пока не прошло на Windows, и фаза 2 не начинается до ворот фазы 0.

Сделано и проверено тестами (`tests/unit/test_long_task.py`, 9 проверок):

- `Limits.long()` — 64 шага, 60 с на провайдера, час на задачу. Потолки подняты **не на
  доверии**: `durable` без журнала даёт `journal_required` до первого предложения модели,
  так что длинная задача без записи своих эффектов просто не начинается.
- Задача владеет durable-запуском: окно планировщика открывает запуск в `WorkflowStore`
  и отдаёт `RunJournal` runner-у. Недоступный журнал не роняет работу — задача идёт
  короткой, без возобновления, и владелец видит это на экране.
- Фазы `running / waiting_approval / waiting_input / done / failed / cancelled` пишутся
  по ходу: видно, ждала ли задача подтверждения или данных. Запись фазы никогда не меняет
  исход; потерянная запись оставляет запуск незавершённым, и это безопасная видимость.
- Возобновление: `planner/resume.py` восстанавливает шаги из журнала. Оттуда приходят
  личность и исход, но не аргументы и не результаты, потому что журнал их не хранит и не
  должен. Следствие, которое нужно назвать прямо: **цель, наблюдённая до перезапуска,
  после него целью не является** — задача обязана посмотреть заново (И5 не развёрнут).
- Шаг, оставшийся `issued`, восстанавливается как таймаут с возможными эффектами, и
  повтор того же ключа отклоняется (`duplicate_effect`). Запуск, который владелец уже
  закрыл, не переоткрывается: возобновляются только незавершённые (`store.unfinished()`).
- Бюджет: `Budget.max_calls`, статус `budget`, счётчик в обоих окнах («Обращений к
  модели: N из M»). Решение по стоимости: считаем **вызовы, а не деньги**. Цену вызова
  пришлось бы переписать с сайта вендора, она молча устареет, а проверить её в этом
  репозитории нечем. Потолок в рублях появится тогда, когда появится проверенный источник
  цен, и не раньше.

Сделано на поверхности (`tests/integration/test_long_task_ui.py`, 6 проверок):

- **Живой чеклист** (`ui/checklist.py`): строка на шаг, из событий `notify()` самого
  runner-а. Шаг закрывается тем статусом, который пришёл; неудавшийся так и остаётся
  на экране. Шаг, который только планировался и не состоялся, со списка снимается.
  Ожидание называет себя: «ждёт подтверждения» или «ждёт ответа».
- **Продолжение прерванной задачи**: список незавершённых запусков и кнопка рядом с
  командой. Возобновление берёт запрос и режим из записи — задача, которая выполнялась,
  не продолжается симуляцией. Шаги до перезапуска показаны отдельной пометкой.
- **Окно подтверждения говорит, сколько осталось.** Это следствие самой фазы: задача
  теперь может ждать час, а снимок действия живёт 60 секунд с момента подготовки
  (`ApprovalStore`). Раньше отлучившийся владелец узнавал об этом, только нажав кнопку и
  получив отказ. Теперь идёт обратный отсчёт, а по его истечении диалог отвечает за
  владельца отказом: держать задачу мёртвым снимком не за что. Авторитет не изменился —
  UI получил чтение остатка времени, а не новую власть выдавать токены.

Не сделано из этой фазы:

- **Очередь подтверждений** — упирается в решение владельца, см. ниже.
- **Живой прогон.** Ворота проверены на локальных инструментах и в симуляции. Настоящая
  длинная задача на живых сервисах ждёт фазы 0 и Windows.

#### Решение, которое нужно владельцу: очередь подтверждений (Р7)

План описывает очередь так: «пока агент работает, накопившееся дорогое показывается
пачкой». Накопиться сейчас нечему. Runner строго последователен — один предложенный
инструмент на шаг, — и на `CONFIRM` он стоит и ждёт. Чтобы дорогое копилось, нужно одно
из двух, и оба разворачивают действующие границы:

1. **Отложить `CONFIRM` и идти дальше.** Тогда план перестаёт быть последовательностью,
   которую модель строит по фактическим исходам: она будет предлагать следующий шаг, не
   зная результата отложенного. Подготовленный снимок при этом живёт 60 секунд, а
   отложенный — дольше, то есть его придётся готовить заново и заново проверять цель.
2. **Выполнять шаги параллельно.** Прямо против правила «один предложенный инструмент на
   шаг» в `AGENTS.md`.

Строить это молча было бы неправильно: очередь стоит на том же месте, где стоят Р1–Р6, и
решение здесь такое же по весу. Пока его нет, поведение остаётся честным: одно дорогое
действие за раз, с точным снимком и видимым остатком времени на ответ.

### Фаза 2 — Сервисы, у которых есть API (2 недели)

Прямой путь к сценариям владельца, и он не требует ни глаз, ни рук.

- `connectors/asana/` — проекты, задачи, создание и правка, сроки, исполнители.
- `connectors/notion/` — поиск, чтение страницы, создание страницы, дописывание блока.
- `connectors/teams/` — чтение чатов и каналов, черновик сообщения, отправка с
  подтверждением. Требует admin consent тенанта: заявка подаётся в фазе 0.
  **Сделано 18.09 наполовину и намеренно:** чаты, черновик и отправка написаны
  ([TEAMS.md](TEAMS.md)) — им не нужно ни одного права с `.All`. Каналы не написаны:
  `ChannelMessage.Read.All` — это те самые внешние ворота, и `AGENTS.md` велит поднимать
  их до фазы, а не внутри неё. Teams просит **отдельное согласие** на тот же аккаунт
  Microsoft, поэтому отказ тенанта не стоит владельцу почты.
- Расширение `connectors/microsoft/` до Excel и файлов OneDrive для отчётов.
  **Сделано 18.09** ([ONEDRIVE.md](ONEDRIVE.md)): поиск файлов, листы книги, чтение
  диапазона и запись диапазона с подтверждением и перечитыванием. Личный OneDrive
  Excel API не обслуживает — нужен рабочий диск.
- `knowledge/harvest.py` получает `mapping.py` каждого нового сервиса: Джон в Asana,
  Джон в Outlook и Джон в Fireflies — один человек.

Приёмочный сценарий фазы — первый из названных владельцем:

```text
«Подготовь всё необходимое к сегодняшней встрече с клиентом»
  → календарь: какая встреча, когда, с кем
  → Fireflies: прошлые разговоры с этим клиентом
  → Asana: открытые задачи по нему
  → Outlook: непрочитанная переписка
  → Notion: страница клиента
  → сводка на экране и голосом, со ссылкой на источник каждого пункта
```

Ворота: каждая строка сводки ссылается на сущность или шаг запуска; повтор задачи не
создаёт вторую задачу в Asana и вторую страницу в Notion; недоступность одного сервиса
оставляет остальные пункты, а не роняет запрос.

**Сделано 18.09** ([MEETING.md](MEETING.md)): кнопка «Подготовить всё к встрече» в окне
команды, `core/meeting.py` — пять `SAFE`-чтений через движок разрешений, в том же порядке
и без участия модели. Клиента определяет приглашение, каждая строка подписана
инструментом и записью сервиса, отказ одного сервиса стоит своего раздела. Сводка ничего
не создаёт, поэтому дублей в Asana и Notion ей взять неоткуда; ворота про повтор остаются
за длинной задачей, где запись и идёт. **Живьём не прогонялось** — нужны подключённые
Outlook, Fireflies, Asana и Notion на одной машине.

### Фаза 3 — Глаза (1,5 недели)

- `windows.read_screen` (`SAFE`) — дерево интерфейса окна: роли, имена, состояния,
  положение. Это основной способ «видеть»: он точнее пикселей, дешевле и не уходит
  в облако.
- `windows.screenshot` (`SAFE`) — снимок **окна**, не рабочего стола. Поля пароля
  вырезаются на стороне адаптера, до возврата изображения.
- `vision.describe` — разбор снимка моделью, когда дерева не хватает: чужой Electron,
  холст, картинка. Отдельное согласие Р6, отдельная запись аудита.
- Наблюдение живёт в задаче: элемент, увиденный десять минут назад, целью не является.

Ворота: снимок не покидает машину без согласия на эту задачу; надпись на экране
«одобри отправку» ничего не одобряет и не становится инструментом; поле пароля не
попадает ни в снимок, ни в дерево, ни в журнал; окно, сменившее содержимое между
наблюдением и действием, аннулирует снимок действия.

### Фаза 4 — Руки (1,5 недели)

- `windows.invoke_element` — нажатие по элементу дерева: кнопка, пункт меню, вкладка,
  флажок. Цель обязана быть наблюдена в этой задаче и совпасть по роли, классу,
  идентификатору и имени.
- `windows.send_keys` — ограниченный набор: навигация, `Ctrl+C/V/S`, `Enter`, `Escape`.
  Не произвольная строка клавиш и не способ обойти границу ввода текста.
- `clipboard.read` (`SAFE`) и `clipboard.write` (`ROUTINE`) — прежнее содержимое
  сохраняется и возвращается после операции.
- `windows.close_window`, `windows.switch_window`, `windows.wait_for` — ожидание
  появления окна или элемента вместо слепой паузы.
- Координатный клик — последний фолбэк: отдельный флаг, подтверждение каждый раз,
  отдельная запись аудита. Если между двумя сервисами есть API, координатный путь
  запрещён тестом.

Ворота: тест архитектурного правила — сценарий, у которого есть API, не имеет права
пройти через буфер обмена или координаты; клик по элементу, которого больше нет,
отказывает, а не промахивается; `Ctrl+V` не вставляет то, что владелец скопировал сам.

### Фаза 5 — Настоящий браузер (1 неделя)

- Постоянный профиль в папке приложения, JavaScript включён, вкладки живут между
  задачами.
- **Вход выполняет владелец.** Окно открывается, владелец вводит логин и пароль сам;
  агент не читает, не хранит и не вводит учётные данные. Cookies остаются в профиле.
- POST и загрузка файлов разрешены, но классифицируются: переход и чтение — `ROUTINE`,
  отправка формы наружу — `CONFIRM`.
- Скачивание — только в разрешённую папку из файловой политики; исполняемые расширения
  не скачиваются.
- Прежний анонимный одноразовый контекст остаётся доступен для чтения незнакомого сайта.

Ворота: страница не может открыть вкладку и увести согласие на другой домен; текст
страницы остаётся данными; выход из сессии владельцем действительно разрывает доступ;
закрытие приложения не оставляет живого браузера.

### Фаза 6 — Один экран (1 неделя)

- Главное окно становится единственным: орб по центру, под ним — текущая задача
  и чеклист шагов, сбоку — последние действия, календарь на сегодня, подключённые
  приложения, настройки.
- Отдельное окно планировщика исчезает; вкладки «Память», «Outlook», «MCP», «Рутины»
  переезжают в настройки и подключения.
- Состояния орба совпадают с состояниями задачи: слушаю, думаю, делаю, жду ответа,
  говорю.
- Подтверждение приходит туда же, где идёт работа, и не открывает третьего окна.

### Фаза 7 — Живой голос (1 неделя)

- Потоковая речь: ответ начинает звучать до того, как дописан.
- Перебивание: слово владельца во время речи останавливает её немедленно.
- Естественный голос становится основным путём, а системный — запасным на случай
  отсутствия сети или ключа.
- Голос отвечает из `core/report.py`, как и сейчас: он произносит, что сделано,
  а не пересказывает ответ сервиса.

### Фаза 8 — Способ работы как память (1 неделя)

Сценарий владельца «разбери встречу → задачи → сроки → сообщение команде» — это
последовательность, которую он одобрил однажды и хочет повторять.

- Завершённый запуск можно сохранить как способ: шаги, инструменты, места данных.
- Повтор подставляет новые данные и идёт тем же путём, спрашивая только там, где
  стоит `CONFIRM`.
- Способ запускается голосом, по расписанию или рутиной из фазы B.

Приёмочный сценарий — второй из названных владельцем:

```text
«Подготовь отчёт по моей работе за эту неделю и отправь его руководителю»
  → Asana: закрытые за неделю задачи
  → Calendar: встречи недели
  → Outlook: отправленные письма по теме
  → документ с отчётом
  → письмо руководителю с вложением
  → СТОП: «Я подготовил письмо и добавил вложение. Отправить?»
  → «Да» → отправка
```

## Порядок и почему такой

```text
0 Реальность → 1 Длинная задача → 2 Сервисы API → 3 Глаза → 4 Руки → 5 Браузер → 6 Экран → 7 Голос → 8 Способ
```

- **0 первой**, потому что всё остальное иначе строится на непроверенном.
- **1 до 2**, потому что новый коннектор без длинной задачи добавляет ещё один вызов
  к восьми доступным и ничего не меняет для владельца.
- **2 до 3 и 4**, потому что API — предпочтительный путь по правилу 1, и три сервиса
  из сценариев владельца API имеют. Строить глаза раньше, чем использованы API, значит
  выбрать худший путь первым.
- **3 до 4**, потому что нажимать можно только то, что увидел.
- **5 после 4**, потому что вход владельца руками в живой браузер — самое чувствительное
  изменение доступа, и оно безопаснее, когда очередь подтверждений и аудит уже несут
  длинные задачи.
- **6 и 7 в конце**, потому что это форма, а не способность; переделывать экран под
  меняющийся набор возможностей — работа дважды.
- **8 последней**, потому что повторять имеет смысл то, что уже один раз прошло целиком.

Итого около 9–10 недель работы плюс внешние одобрения: admin consent Microsoft для
Teams и доступы к Asana и Notion.

## Что по-прежнему не входит

Каналы вне машины (мессенджер как второй интерфейс), мобильные приложения,
multi-tenancy, произвольное выполнение кода, написанного моделью, скрытое наблюдение
за владельцем и поддержка всех программ без разбора. `BLOCKED` не открывается никогда.

## Ворота качества для каждой фазы

Правила репозитория не меняются: focused-тесты → полный набор → Ruff → `ruff format`
→ `mypy --strict` → живой запуск → обновлённые документы и честный отчёт.

Дополнительно на этот план:

- Mock-тест не доказывает работу Windows, микрофона, почты и модели.
- Каждый новый инструмент рождается на `CONFIRM` и опускается до `ROUTINE` только
  осознанным решением, записанным в этот документ.
- Каждый новый коннектор: тесты отказа аутентификации, таймаута, дубля и отмены.
- Каждый новый сценарий: тест на пропавшие данные, на отказ инструмента, на отмену
  посреди работы и на повтор без дубля.
